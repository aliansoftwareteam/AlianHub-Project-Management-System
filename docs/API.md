## Base URL and versions

Every path is relative to the address your AlianHub instance is served from, for example `https://hub.example.com`. There is no separate API host.

| Prefix | What it is |
|---|---|
| `/api/v2` | The API integrations should use. This reference documents the part of it a token can call. |
| `/api/public-v1` | A small read-only namespace that accepts an API token and nothing else. |
| `/api/v1` | The web app's own API. It is listed in the appendix so nothing is hidden, but it follows the web app and may change without notice. |

Request bodies are JSON (`Content-Type: application/json`). A body larger than the server's limit (2 MB unless the instance raises `BODY_LIMIT`) is refused.

## Authentication

### Personal access tokens

A personal access token starts with `ahp_` and is shown once, when it is created. Send it as a bearer token, together with the id of the workspace the request is for:

```http
GET /api/v2/api-tokens/me
Authorization: Bearer <token>
companyid: <company id>
```

A token acts as the person who created it. It reads what that person can open in the web app and changes what that person's role allows; it is never a way past project or sprint visibility. A token stops working on its next call when it is revoked, when it expires, or when its person is removed from the workspace.

A token is created from a signed-in session, in the web app. A token cannot create, change or delete tokens: the token management routes answer 403 to a token, except `GET /api/v2/api-tokens/me`.

### The `companyid` header

A token belongs to one workspace. Every request made with a token carries that workspace's id in the `companyid` header, as 24 hexadecimal characters. A missing or malformed header is a 401.

### Scopes

A token carries the scopes `read` and `write`. `GET`, `HEAD` and `OPTIONS` requests need `read`; every other method needs `write`, including a `POST` that only reads. A token without the scope a request needs gets a 403. A token created with no scopes named holds both.

### Tokens limited to projects

A token can be created limited to some projects. Such a token is refused, with 403 and `code: "token_limited_to_projects"`, on every route that cannot hold it to that list. Of the routes documented here, these accept it:

- `GET /api/v2/api-tokens/me`
- `GET /api/public-v1/projects`
- `GET /api/public-v1/tasks`
- `GET /api/public-v1/tasks/:key`
- `POST /api/v2/tasks/everything`

On those routes it reads only its own projects; a project outside the list answers "not found". Each route below says whether it accepts such a token.

### Agent tokens

A token created for an AI agent is an agent token. On top of everything above, an agent token is refused on every `DELETE` request, on the bulk task route, and on billing, member, permission and token management routes. Those refusals are 403 and are recorded in the audit log.

### Token lifetime

A token can be given an expiry of 1 to 365 days when it is created. An instance running with `API_TOKEN_STRICT` requires both an expiry and at least one scope, can lower the longest lifetime with `API_TOKEN_MAX_DAYS`, and stops tokens that have no expiry 30 days after strict mode began (or after the token was created, if later). Without strict mode a token with no expiry keeps working until it is revoked.

### OAuth

OAuth is offered for the MCP endpoint (`/mcp`) when the instance turns `MCP_OAUTH` on, and only there: an OAuth access token is not accepted by the REST routes in this reference. Its scopes are `tasks:read`, `tasks:write`, `projects:read`, `docs:read`, `time:read`, `time:write`, `tasks:manage`, `docs:manage`. By default an access token lasts 15 minutes, a refresh token 30 days and a grant at most 90 days. See `docs/MCP-AGENT-GUIDE.md`.

## Responses and errors

A success is a JSON object with `status: true`, a human-readable `statusText`, and the result in `data`:

```json
{ "status": true, "statusText": "Pages fetched.", "data": [] }
```

A few routes put a value beside `data` instead of inside it (a new task's `id`, a list's `hasMore`); each route below shows its own response.

A failure is a JSON object with `status: false` and the reason in `statusText`, `message` or both:

```json
{ "status": false, "statusText": "Page not found." }
```

Some failures add `error`, a machine-readable `code`, the `permission` key that was missing, or the `field` that was refused.

**Status codes.** The web app expects HTTP 200 on a handled failure and reads `status` from the body. A request made with an API token gets a real status code instead: when a handler answers 200 with `status: false`, the server changes the status line to the matching 4xx and adds the header `X-Status-Mapped: 1`. The body is not changed. Any other caller can ask for the same with the header `Prefer: status-codes`. The code is the handler's own `statusCode` when it sets one, and is otherwise read from the text: "not found" is 404, a permission refusal is 403, "already" or "duplicate" is 409, a token or session problem is 401, and anything else is 400. Check `status` in the body as well as the status code.

| Status | Meaning |
|---|---|
| 400 | The request was refused: a missing or malformed field, an unknown key, a value out of range. |
| 401 | No token, a token that is invalid, expired or revoked, or no valid `companyid` header. |
| 403 | The token lacks the scope, the person's role lacks the permission, or the token may not use the route. |
| 404 | The thing does not exist, or the caller may not see it. The two are answered alike on purpose. |
| 409 | The request conflicts with what is stored. |
| 429 | Rate limited. See [Rate limiting](#rate-limiting). |
| 500 | The server failed. The body carries `status: false`. |

## Rate limiting

There is one limit per client address, across all API routes: 1000 requests per 60 seconds unless the instance sets `GLOBAL_RATE_LIMIT_PER_MIN` (which can also turn it off). Static files are not counted. A request over the limit is answered with 429, a `Retry-After` header in seconds, and:

```json
{
  "status": false,
  "code": "server_busy",
  "statusText": "The server is busy. Try again in a moment.",
  "message": "The server is busy. Try again in a moment.",
  "retryAfter": 12
}
```

On a 429, wait `retryAfter` seconds and send the same request again. The response headers `RateLimit-Limit`, `RateLimit-Remaining` and `RateLimit-Reset` show where the caller stands.

## Ids and dates

An id is 24 hexadecimal characters, sent and returned as a string. A value that is not a well-formed id where one is expected is a 400, or reads as "not found".

A date is returned as an ISO 8601 string in UTC, for example `2026-10-01T09:30:00.000Z`. Where a route accepts a date it accepts an ISO 8601 string; a route that also accepts a time in milliseconds says so.

Field names are the stored ones and are not uniform: a task carries `TaskName`, `ProjectID` and `Task_Priority` beside `sprintId` and `statusKey`. Use the names exactly as each route shows them.

## Pagination

Three styles are in use. Each route says which one it follows.

| Style | How it works | Used by |
|---|---|---|
| Cursor | Send the `nextCursor` of the page before as `cursor`. `nextCursor` is `null` on the last page. | `POST /api/v2/tasks/everything` |
| Skip and limit | Send `skip` and `limit`. The response carries `hasMore` and `nextSkip`. | `GET /api/v2/webhooks/:id/logs` |
| Limit only | Send `limit`, up to the route's cap. The newest rows come first and there is no next page. | `GET /api/public-v1/tasks`, `GET /api/v2/agents/runs`, `GET /api/v2/agents/proposals` |

Routes that are not in this table return the whole list.

## Webhook deliveries

A webhook posts task events to a URL you choose. The events are `task.created`, `task.updated`, `task.deleted`, `task.archived`, `task.restored`; `*` subscribes to all of them. The formats are `json`, `slack`, `discord`. Webhooks are managed with the routes under [Webhooks](#webhooks).

A delivery in the `json` format is a `POST` with this body:

```json
{
  "event": "task.updated",
  "companyId": "<company id>",
  "deliveredAt": "2026-10-01T09:30:00.000Z",
  "changedFields": ["Task_Priority"],
  "data": {
    "_id": "<task id>",
    "TaskKey": "WEB-12",
    "TaskName": "Write the release notes",
    "statusType": "active",
    "Task_Priority": "HIGH",
    "ProjectID": "<project id>",
    "sprintId": "<list id>",
    "AssigneeUserId": ["<user id>"],
    "assigneeNames": ["Sample Person"],
    "updatedAt": "2026-10-01T09:30:00.000Z"
  }
}
```

`data` is a fixed set of task fields, never the whole stored task. `previous` is added, with the same shape, when the server has delivered this task before. Each delivery carries the headers `X-AlianHub-Event`, `X-AlianHub-Delivery-Attempt` and `X-AlianHub-Signature`. The signature is `sha256=` followed by the HMAC-SHA256 of the raw request body, keyed with the secret returned when the webhook was created; compute it over the bytes received and compare before trusting a delivery. Changes to one task within a couple of seconds arrive as one delivery. A delivery that fails with a network error or a 5xx is sent once more, 30 seconds later.

## Identity

Who a token is, and what that person may do.

### Who am I

`GET /api/v2/api-tokens/me` · stable

Returns the person and the workspace behind the token, with that person's role and permissions.

Call it once after connecting, to check that the token and the `companyid` header are right.

|  |  |
|---|---|
| Auth | Session or API token with the `read` scope |
| Token limited to projects | Accepted, and held to its projects |

**Request**

```http
GET /api/v2/api-tokens/me
Authorization: Bearer <token>
companyid: <company id>
```

**Response**

```json
{
  "status": true,
  "statusText": "Identity resolved.",
  "data": {
    "userId": "<user id>",
    "companyId": "<company id>",
    "name": "Sample Person",
    "email": "person@example.com",
    "timeZone": "Europe/London",
    "roleType": 3,
    "permissions": { "task.task_list": true, "task.task_create": true, "project.project_create": null },
    "scopes": ["read", "write"],
    "tokenName": "Reporting script"
  }
}
```

| Field | Description |
|---|---|
| `roleType` | `1` is the owner, `2` an admin, `3` a member, `0` a guest. |
| `permissions` | The person's workspace-wide answer for the permission keys the server checks most: `true` may change, `false` may only read, `null` has no access, and `1` or `2` mean "own" or "everyone" on the keys that take a choice. A project with its own rules can answer differently. |
| `scopes` | The token's scopes. Empty when the request was made with a session. |

**Errors**

| Status | When |
|---|---|
| 401 | No token, a token that is invalid, expired or revoked, or no valid `companyid` header. |
| 403 | The token lacks the `read` scope, or its person is no longer a member of the workspace. |
| 429 | Too many requests from this address. Wait `retryAfter` seconds and send it again. |

## Tasks

Creating a task and changing one. Both routes take the bodies the web app sends, so their field names follow the stored task. To read tasks, use [Everything](#everything) or the [Read-only token API](#read-only-token-api).

### Create a task

`POST /api/v2/tasks` · beta

Creates a task, or a subtask when `data.ParentTaskId` names a parent.

The body is the one the web app sends: the task under `data` and the project it goes into under `projectData`. The server sets the company and the acting person itself, whatever the body says. Under a parent, the project, list and folder are taken from the parent, and the parent must be in the project the body names.

The task's key is assigned after the task is saved, from the project's code and its next number. Read the task back to learn it.

|  |  |
|---|---|
| Auth | Session or API token with the `write` scope |
| Token limited to projects | Refused |
| Permission | `task.task_create` |

**Body**

| Field | Type | Required | Description |
|---|---|---|---|
| `data.TaskName` | string | yes | The task's name. |
| `data.TaskKey` | string | yes | A placeholder such as `-`. The server replaces it with the real key. |
| `data.TaskType` | string | yes | One of the project's task types, by its value. |
| `data.TaskTypeKey` | number |  | The key of that task type. |
| `data.ProjectID` | id | yes | The project the task goes into. |
| `data.sprintId` | id |  | The list the task goes into. |
| `data.sprintArray` | object |  | `{ id, name }` of that list, with `folderId` and `folderName` when the list sits in a folder. |
| `data.folderObjId` | id |  | The folder, when the list sits in one. |
| `data.status` | object |  | The status as the project defines it: `{ text, key, type }`. |
| `data.statusKey` | number |  | The key of that status. |
| `data.statusType` | string |  | The type of that status, for example `default_active`. |
| `data.Task_Priority` | string |  | The priority, for example `MEDIUM`. |
| `data.AssigneeUserId` | id[] |  | The assignees. Each must hold a seat in the workspace. |
| `data.watchers` | id[] |  | The watchers. Each must hold a seat in the workspace. |
| `data.Task_Leader` | id |  | The task's lead. Must hold a seat in the workspace. |
| `data.DueDate` | date |  | The due date, or an empty string. With a date, send `data.dueDateDeadLine` as `[{ date }]`. |
| `data.startDate` | date |  | The start date. |
| `data.ParentTaskId` | id |  | The parent, for a subtask. Empty for a top-level task. |
| `data.isParentTask` | boolean |  | `true` for a top-level task, `false` for a subtask. |
| `data.deletedStatusKey` | number |  | `0` for a live task. |
| `projectData._id` | id |  | The same project as `data.ProjectID`. |
| `projectData.ProjectName` | string |  | The project's name, used in the notification. |
| `projectData.ProjectCode` | string |  | The project's code. The task's key starts with it. |
| `indexObj` | object |  | Where the task sits in the web app's grouped lists: `{ indexName, searchKey, searchValue }`. `indexName` is one of `groupByStatusIndex`, `groupByPriorityIndex`, `groupByAssigneeIndex`, `groupByDueDateIndex`. |

**Request**

```http

companyid: <company id>
Content-Type: application/json

{
  "data": {
    "TaskName": "Write the release notes",
    "TaskKey": "-",
    "TaskType": "task",
    "TaskTypeKey": 1,
    "ProjectID": "<project id>",
    "sprintId": "<list id>",
    "sprintArray": { "id": "<list id>", "name": "Sprint 12" },
    "status": { "text": "To Do", "key": 1, "type": "default_active" },
    "statusKey": 1,
    "statusType": "default_active",
    "Task_Priority": "MEDIUM",
    "AssigneeUserId": [],
    "watchers": [],
    "DueDate": "",
    "dueDateDeadLine": [],
    "ParentTaskId": "",
    "isParentTask": true,
    "deletedStatusKey": 0
  },
  "projectData": { "_id": "<project id>", "ProjectName": "Website", "ProjectCode": "WEB" },
  "indexObj": { "indexName": "groupByStatusIndex", "searchKey": "statusKey", "searchValue": 1 }
}
```

**Response**

```json
{ "status": true, "statusText": "Task created successfully.", "id": "<task id>" }
```

The new task's id is in `id`, beside `status`, not inside `data`.

**Errors**

| Status | When |
|---|---|
| 400 | The body is not an object, carries a key that is not accepted, names something that is not an id where an id is expected, names a person who holds no seat in the workspace, the parent cannot take another level of subtasks, or the workspace's plan allows no more tasks in the list. |
| 401 | No token, a token that is invalid, expired or revoked, or no valid `companyid` header. |
| 403 | The token lacks the `write` scope, or its person is no longer a member of the workspace. A token limited to projects is refused here. The person's role lacks the permission the route needs. |
| 404 | The parent task does not exist, or is not in the project the body names. |
| 429 | Too many requests from this address. Wait `retryAfter` seconds and send it again. |

### Change a task

`PATCH /api/v2/tasks` · beta

Changes one task. `action` names the change, and the other keys of the body depend on it.

Each action reads the task it changes from the id shown under Ids, and answers 404 when the caller cannot see that task. The first id listed is the task; the others are the further tasks, people or projects the action names.

The server fills in the acting person, the company and, where an action uses them, the stored names of the task and its project. Keys an action does not use are dropped rather than refused, so the bodies the web app sends keep working. Where a key is followed by names in brackets, those are the only fields of that object the action writes.

Some actions take `isUpdateTask`. Leave it out. Sent as `false` it records history for a change another request already made, and is refused with 409 unless the stored task already holds that value.

|  |  |
|---|---|
| Auth | Session or API token with the `write` scope |
| Token limited to projects | Refused |
| Permission | One per action, in the table below |

**Body**

| Field | Type | Required | Description |
|---|---|---|---|
| `action` | string | yes | One of the actions in the table below. |

**Actions**

| `action` | Permission | Ids | Body keys kept | Notes |
|---|---|---|---|---|
| `updateStatus` | `task.task_status` | `task._id`, `prevStatus.taskId` | `newStatus` (`status`, `statusKey`, `statusType`), `prevStatus`, `projectData`, `task`, `isUpdateTask` | Sets the status. `newStatus` holds the status as the project defines it. |
| `updatePriority` | `task.task_priority` | `taskData._id`, `priorityObj.taskId` | `firebaseObj` (`Task_Priority`, `Updated_At`), `projectData`, `taskData`, `priorityObj`, `isUpdateTask` | Sets the priority. |
| `updateAssignee` | `task.task_assignee` | `taskData._id` | `firebaseObj` (`AssigneeUserId`), `projectData`, `taskData`, `employeeName`, `type`, `isUpdateTask` | `type` is `assigneeAdd`, `assigneRemove` or `replace`. |
| `updateDueDate` | `task.task_due_date` | `task._id` | `commonDateFormatString`, `timeZone`, `firebaseObj` (`DueDate`, `dueDateDeadLine`), `project`, `task`, `obj`, `isUpdateTask` |  |
| `updateStartDate` | `task.task_due_date` | `task._id` | `commonDateFormatString`, `timeZone`, `firebaseObj` (`startDate`), `project`, `task`, `obj`, `isUpdateTask`, `isHistory` |  |
| `updateTaskType` | `task.task_type` | `taskData._id` | `newStatus` (`TaskType`, `TaskTypeKey`, `taskTypeImage`, `oldTaskTypeImage`, `taskTypeName`), `prevStatus`, `projectData`, `taskData`, `isUpdateTask` |  |
| `updateDescription` | `task.task_description` | `task._id` | `companyId`, `projectData`, `sprintId`, `task`, `text` | Sets the description from `text.blocks` and `text.text`. |
| `updateTaskTotalEstimate` | `task.task_estimated_hours` | `taskData._id` | `firebaseObj` (`totalEstimatedTime`), `projectData`, `taskData`, `obj` |  |

## Everything

One list of tasks across every project the caller can read, with filters, grouping, sorting and a cursor, and the caller's saved views of that list.

### List tasks across projects

`POST /api/v2/tasks/everything` · beta

Lists tasks from every project the caller can read, filtered, grouped, sorted and paged.

It is a read sent as a `POST`, so a token needs the `write` scope. Every key of the body is optional, and an unknown key at any level is a 400.

Whatever the body says, the server reads only projects the caller can open and whose task list their role may read, leaves out closed, archived and restricted projects, other people's personal lists, private lists the caller is not on, and deleted or archived tasks.

|  |  |
|---|---|
| Auth | Session or API token with the `write` scope |
| Token limited to projects | Accepted, and held to its projects |

**Body**

| Field | Type | Required | Description |
|---|---|---|---|
| `filter.status` | array |  | Up to 100 status names or whole-number keys. Names match exactly. |
| `filter.statusType` | string[] |  | Any of `default_active`, `active`, `done`, `close`, `default_close`. |
| `filter.assignee` | array |  | Up to 100 user ids, or `unassigned`. |
| `filter.priority` | string[] |  | Up to 100 priority names. |
| `filter.dueDate` | object |  | `{ from, to, none }`. `from` and `to` are ISO dates or times in milliseconds. `none: true` means "no due date" and cannot be combined with a range. |
| `filter.taskType` | array |  | Up to 100 task type names or keys. |
| `filter.tags` | string[] |  | Up to 100 tag ids. |
| `filter.search` | string |  | Text of at most 200 characters. |
| `filter.projectIds` | id[] |  | Up to 500 project ids. It can only narrow what the caller may read. |
| `filter.sprintIds` | id[] |  | Up to 100 list ids: tasks that live in one of them or were added to one. A list the caller cannot open is ignored. |
| `group` | string |  | `none`, `status`, `assignee`, `project`, `priority` or `dueDate`. `none` when left out. |
| `sort` | object |  | `{ by, dir }`. `by` is `updatedAt` or `DueDate`; `dir` is `asc` or `desc`. Newest update first when left out; `DueDate` defaults to `asc`. |
| `cursor` | string |  | The `nextCursor` of the page before. |

## Appendix: every other route

Every route the server registers that is not documented in full above, with every optional module switched on. `internal` routes are not for integrations; every `/api/v1` route is one unless the meta file says otherwise. `undocumented` routes have no description here yet; nothing about them is promised.

The Auth column is the guard the route sits behind. `Session or token` routes accept the web app's session or an API token. `Session` routes refuse a token. `Instance admin` routes are for the person who runs the server. `No login guard` routes are sign-in and sign-up, pages opened by a secret link, and endpoints that check a credential of their own, such as `/mcp` and `/scim/v2`. A handler can refuse more than its guard does.
